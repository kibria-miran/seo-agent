C3. DuckDuckGo access — ddgs vs html endpoint; robots; throttle; UA; ToS.
-------------------------------------------------------------------------------
CONFIRMED the README/requirements and code diverge, and robots is not checked
for search/API endpoints.
- requirements.txt and pyproject.toml declare ddgs (requirements.txt:202,203;
  pyproject.toml:13), but `grep -rn "import ddgs|from ddgs"` finds ZERO uses
  in src/, tests/ or third_party/. ddgs is dead weight as declared.
- Actual access: src/sources/serp.py:25 SERP_URL =
  "https://html.duckduckgo.com/html/"; SerpSource.fetch builds q=<query>,
  GETs via fetch.http_get and parses blocks with BeautifulSoup.
  src/sources/suggest.py:21
  SUGGEST_URL = "https://suggestqueries.google.com/complete/search";
  SuggestSource GETs client=firefox&q=...&hl=en-GB.
- fetch.py: http_get(url, respect_robots=False) is the DEFAULT (line 68);
  robots is only checked when respect_robots=True, i.e. fetch_page/fetch_text
  (page crawls). Search/API endpoints pass respect_robots=False deliberately,
  documented at fetch.py:50-56 and serp.py module docstring — "not page
  crawls but still throttled and GET-only".
- Throttle: yes — shared per-host 2s delay via throttle() (fetch.py:45-57);
  UA is the honest config.USER_AGENT (config.py:33). Both endpoints count
  toward MAX_FETCHES via _module_state["fetches"].
- robots.txt for duckduckgo.com/html.duckduckgo.com and
  suggestqueries.google.com is NEVER consulted (endpoint calls pass
  respect_robots=False, and _robots_allowed does not run). r.b. the 2s/host
  delay DOES apply to serp/suggest since it is inside http_get.
- ToS risk: html.duckduckgo.com/html/ is an undocumented, unauthenticated
  HTML endpoint. Scraping it violates neither law nor DuckDuckGo's published
  API terms outright (no key required, no explicit prohibition) but is
  fragile (markup change silently yields 0 results, which the code treats as
  "no SERP", not an error) and is in tension with ddgs, which is the
  maintained, ToS-tolerant path (it uses the same endpoint family but with
  its own parsing/verification; and pulls its own dependencies we already
  hash into requirements.txt). Google Suggest client=firefox is similarly
  undocumented. Verdict: functionality works; legal/ToS posture is
  "grey-scrape", and the unused ddgs dependency proves the project knew
  about the cleaner route and never wired it.
- Suggest
  - same robots story, same throttle, same UA
  - endpoint undocumented; JSON shape defensively parsed; malformed payload
    -> SourceError -> pipeline logs & skips (non-fatal).
Proposed fix: either wire ddgs (declared dep, maintained parser) and keep
html endpoint as fallback behind config, or delete ddgs from requirements;
separately, lift the robots/throttle posture decision into an explicit
config flag (e.g. respect_robots on endpoint calls) and document the choice;
add a soft failure signal when the SERP parser returns 0 blocks.
Effort: medium.

  AuditSnapshot (pages) + clusters + competitor_pages + serp; GSC data never
  reaches it. GSC acts purely as a keyword-demand multiplier in build-up
  (src/pipeline.py:140-149).
- There is NO query->page mapping anywhere in the repo. Suggest/SERP/
  competitor/GSC all produce keyword-level evidence only; confidence weights
  in backlog.confidence_for() (src/backlog.py:59) depend on source count,
  not on page attribution.

  query,page). Still keyless in dollars but needs OAuth client config, which
  is new account surface; keeps Source interface but adds an auth dependency
  unlike every other source. Not recommended first.
  Recommend A; B only if A proves insufficient.
